## What the GIF demonstrates

- A complete playable loop: Title -> Stage Select -> Battle -> Result/Retry.
- Tactical RPG readability: side rosters, central battlefield, command area, recent actions, and enemy intent are separated instead of stacked in one debug panel.
- Player decision surface: Attack/Guard/skills appear through the selected-ally command pattern, matching tactical-RPG expectations.
- Combat feedback: hit sparks, impact rings, screen shake profiles, damage/status popups, idle bob, and hit reactions support short video/GIF readability.
- Portfolio evidence beyond visuals: the result panel exposes measurable design values such as damage dealt/taken, skill/guard counts, rank, reward, pace, and survival.

## Data-driven systems represented

| Visible in capture | Data/source used by runtime | Why it matters |
|---|---|---|
| Stage card and battle objective | `StageData`, `EnemyData` | Stage preview and battle logic share one data source instead of duplicated text. |
| Enemy intent and boss pressure | `EnemyPatternData`, stage modifier fields | Enemy behavior can be tuned without rewriting UI text each time. |
| Skill AP/element/status output | `SkillData`, balance config values | Skill cost, power, element, and status are explicit design data. |
| Result rank/reward/tip | `BattleResultData`, `BattleResultEvaluator`, `BattleResultPresenter` | Evaluation rules are separated from battle flow and can be explained as portfolio architecture. |
| HP/AP bars and status labels | `BattleUI` bound to battle state | Runtime values are displayed as reviewable feedback, not only stored internally. |

## Technical decisions worth explaining

1. **Generated scenes with validators**
   - The battle and flow scenes are generated by editor tools so UI wiring can be recreated consistently.
   - Validators check required UI references, scene objects, and flow elements after each change.

2. **Small classes before large framework complexity**
   - The project keeps systems beginner-readable: data classes, presenter/evaluator splits, and editor menu tests instead of a large custom framework.

3. **Capture-first polish**
   - Recent work prioritized what appears in a 8-15 second portfolio clip: clear HUD hierarchy, pixel standees, hit feedback, idle motion, and result evidence.

4. **README GIF is reproducible**
   - `Docs/Captures/build_readme_gif.py` rebuilds the GIF from committed PNGs, avoiding large raw video files in the repo.
